# 错误处理规范

> 本文件是**错误处理规范的唯一真源**。
> 上游索引：[`AGENTS.md`](../../AGENTS.md)（L0 常驻：铁律 + 规则索引）
> 后端契约来源：[`ai-picture-editor-backend/docs/接口响应体.md`](../../../ai-picture-editor-backend/docs/接口响应体.md)
> 关联规范：[`directory-structure.md`](./directory-structure.md)（`lib/` 承担归一化与 401 钩子）

## 适用范围

前端所有 HTTP 请求与 SSE 连接的：**错误识别 → 归类 → 展示 / 恢复动作**。
不含画布内部异常（属 M3 领域错误，另行约定）。

---

## 1. 背景与前提（先接受这四条，后面的规则才有意义）

1. **后端错误统一在 `detail` 字段**：无自定义异常处理器，业务错误为 `{"detail":"中文文案"}`，422 为 `{"detail":[{loc,msg,type}]}`。
2. **后端不可改**：按 ROADMAP，后端由既 有实现提供，前端只适配、不推动改造。
3. **因此不采用 RFC 9457 / problem+json**：后端不产出该格式，解析它是死代码；且后端不提供任何 `type` / `code` 机器码。
4. **鉴权为 httpOnly Cookie，无 refresh token**（有效期 24h）：前端读不到凭证、也刷不了，401 只能「清态 + 重新登录」。

> 判断口径：**能在前端闭环解决的，就不要去改后端**。

---

## 2. 核心规则

| # | 规则 |
| --- | --- |
| R1 | **HTTP 状态码是唯一的机器主键**，`detail` 只作展示文案。 |
| R2 | **禁止解析 `detail` 文案做分支**（中文文案会变，解析必碎）。 |
| R3 | 409 的子类型歧义，用**请求上下文**或**响应体自带标志位**消歧，不用文案。 |
| R4 | 所有请求错误归一为统一错误类型（下表契约），**UI 按分类码分派，不按 `status` 散写 if**。 |
| R5 | 401 由统一钩子处理；**`login` / `register` 的 401 必须排除在跳转之外**。 |
| R6 | Query 与 Mutation 的重试策略不同：**Mutation 默认一律不自动重试**。 |
| R7 | 传输层只负责「发出去 + 归一错误」，**不碰服务端状态**（缓存 / 失效 / 重试归 TanStack Query）。 |

## 3. 错误分类表（判定主干）

| HTTP | 分类码 | 预料中 | 可重试 | 语义 | 前端动作 |
| --- | --- | --- | --- | --- | --- |
| 401 | `UNAUTHENTICATED` | ✅ | ❌ | 未登录 / 会话过期 | 清用户态 + 跳登录（**登录、注册接口除外**，见第 5 节） |
| 404 | `NOT_FOUND` | ✅ | ❌ | 不存在**或不属于当前用户**（后端刻意不区分，避免探测） | 按请求上下文定展示层级（L2 / L4） |
| 409 | `CONFLICT` | ✅ | ❌ | 业务状态冲突 | 刷新状态后让用户重做；能事前判断的先判断 |
| 413 | `PAYLOAD_TOO_LARGE` | ✅ | ❌ | 上传超过 20MB | L1 上传控件内联提示 |
| 422 | `VALIDATION` | ✅ | ❌ | 参数不合法（含 pydantic 校验） | L1 字段级（`loc` → 字段） |
| 202 | — | — | — | **异步受理，不是错误** | 转 SSE / 轮询跟进 |
| 5xx | `SERVER` | ❌ | ✅ 退避 | 服务端故障 | L3 Toast + 重试按钮 |
| 网络 / 超时 | `NETWORK` / `TIMEOUT` | ❌ | ✅ 退避 | 链路问题 | L3 Toast + 重试按钮 |
| 取消 | `ABORTED` | — | — | `AbortController` 主动取消 | L5 静默，不计为故障 |
| 其他 | `UNKNOWN` | ❌ | ❌ | 未归类 | 兜底提示 + 上报 |

> **预料中**决定措辞（具体业务文案 vs 通用兜底）；**可重试**决定是否自动重试与是否给重试按钮。二者独立。

### 409 歧义的消歧方式（R3 落地）

后端 409 混了多种语义，一律靠这两招解决，**不解析文案**：

| 场景 | 消歧方式 |
| --- | --- |
| 「没有可撤销 / 可重做的操作」 | **事前判断**：响应体自带 `can_undo` / `can_redo`，先判断再决定按钮可用性，根本不等 409 |
| 「画布已更新，请重新选择」 | **请求上下文**：前端知道自己调的是 `/selection`，据此判定为「版本过期 → 重拉状态」 |

## 4. 统一错误契约（前端内部，非传输格式）

所有请求错误归一为此结构，UI 与之解耦——后端换格式只改归一化一处。

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `code` | 由 `status` 映射（纯前端派生，约 20 行映射表） | **机器主键**，UI 分支的唯一依据 |
| `expected` | 由 `code` 派生 | 决定措辞：具体业务文案 vs 通用兜底 |
| `retryable` | 由 `code` 派生 | 决定 Query 重试与是否展示重试按钮 |
| `message` | 后端 `detail`（422 取数组并聚合） | 展示文案，**原样呈现** |
| `fields` | 422 的 `detail[].loc` + `msg` | 字段级错误定位 |
| `status` | 响应状态码 | 排查与兜底分支 |
| `payload` | 原始响应体 | 排查，不参与 UI |

> `code` 是**前端派生值**，不依赖后端任何字段——这是「约定错误响应体」的落点：约定在归一化层，不在传输线上。

---

## 5. 401 处理规则（R5 落地）

因 httpOnly + 无 refresh：401 **不可能**静默刷新重试，唯一动作是「清态 + 重新登录」。但必须区分场景：

| # | 场景 | 401 的真实含义 | 正确动作 | 必须避免的坑 |
| --- | --- | --- | --- | --- |
| a | 启动探测 `GET /me` | 本来就是游客 | 视为**正常未登录态**，走路由守卫 | 别当错误上报 / 弹 Toast |
| b | 会话中任意请求 | 会话过期（24h） | 清用户态缓存 + 跳登录 + 提示「登录已过期」 | 并发多个请求同时 401 → **要去重，只跳一次** |
| c | `POST /auth/login` / `register` | **账号或密码错误** | **内联表单错误** | ⚠️ 必须排除在全局跳转外，否则登录页自我重定向，用户永远看不到错误 |
| d | SSE 连接 | 会话过期 | 关流 + 跳登录 | 不走 HTTP 拦截器（EventSource 是独立通道） |

**钩子约定**：401 的跨层副作用用「钩子 / 回调」在 `app/` 装配处注入，`lib/` 不得反向依赖路由层（见 `directory-structure.md` 耦合边界）。

## 6. 展示层级

| 层级 | 承载形态 | 适用 |
| --- | --- | --- |
| **L1 字段级** | 控件下方行内提示 | 422（`loc` 定位到字段）、413（上传超限） |
| **L2 区块 / 行内** | 面板内提示条 | 409（撤销不可用 → 按钮置灰 + 说明）、子资源 404 |
| **L3 全局 Toast** | 轻提示 + 动作按钮 | 5xx、网络、超时 → 附「重试」按钮 |
| **L4 路由 / 整页** | 占位页或错误边界 | 主资源 404（会话不存在 → 回列表）；未捕获异常 → ErrorBoundary |
| **L5 静默** | 仅日志 | 后台 refetch 失败、SSE 保活帧异常、主动取消 |
| **导航动作**（不属于展示层） | 路由跳转 | 401 |

> **层级由「分类码 + 请求上下文」共同决定**，不由分类码单独决定：同为 404，`GET /sessions/{id}` 是 L4，刷新某个素材是 L2。

---

## 7. 重试策略（Query vs Mutation）

| 请求类型 | 自动重试 | 理由 |
| --- | --- | --- |
| **Query**（GET 类） | ✅ 仅对 `retryable` 为真者，退避重试，次数上限 2 | GET 安全，重跑无害 |
| **Mutation**（POST / PATCH / DELETE 类） | ❌ **默认一律不重试** | 网络层失败时服务端可能已受理，重试会产生重复任务（如重复创建 run） |
| 例外 | 已确认幂等的写操作（如 `DELETE /{id}/selection`）可单独开启重试 | 幂等性给的是「重试通行证」，不改变其 Mutation 身份 |

> 后端契约中暂无 429 / 限流。若后续补充，需加入可重试集合并读取 `Retry-After`。

---

## 8. 明确禁止的反例

- ❌ 解析后端 `detail` 中文文案做业务分支（`detail` 只用于展示）。
- ❌ 假设后端存在 `success` / `message` 信封（真实后端没有，相关判断是死代码）。
- ❌ 在组件里按 `status` 散写 if 判断错误类型（应统一按 `code` 分派）。
- ❌ 把 DELETE / PUT 当作 Query 使用（会被窗口聚焦、断线重连、预取重复执行）。
- ❌ 全局 401 无条件跳登录（会导致登录页自我重定向，用户看不到密码错误提示）。
- ❌ Mutation 开启自动重试（会重复创建资源）。
- ❌ 导出 / 二进制接口设 `blob` 响应类型后直接读错误（错误体同样会变成 blob，会显示乱码）。
- ❌ 认为健康检查返回 200 就代表健康（后端失败也返回 200，错误藏在 body 的 `error:` 前缀里）。

## 10. 自检清单

新增 / 修改请求相关代码后逐项确认：

- [ ] 未解析 `detail` 文案做分支，只用它展示
- [ ] 分类依据来自 HTTP 状态码映射出的 `code`
- [ ] 组件按 `code` 分派，没有散写 `status` if
- [ ] 展示层级由「分类码 + 请求上下文」共同决定
- [ ] 401 走统一钩子；`login` / `register` 已排除在跳转之外
- [ ] Mutation 未开启自动重试（除非确认幂等且有意为之）
- [ ] 导出 / 二进制接口已处理错误体也是 blob 的情况
- [ ] 健康检查按 body 判定，未把 200 直接当作健康
- [ ] 409 未靠文案区分，用的是请求上下文或 `can_undo` 类标志位
- [ ] 归一化逻辑仍在 `lib/`，未反向依赖路由层
