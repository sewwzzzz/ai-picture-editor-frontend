# 状态管理

## 目的

1. 统一数据源，避免数据散落 -- 数据同步

2. 解耦修改状态与展示视图 -- 数据修改

3. 状态变化可预测，可追踪。"触发动作 → 修改状态 → 视图更新"单向数据流（如 Redux、Vuex、Pinia）-- 数据修改

4. 跨组件/路由共享与持久化 -- 数据存活 

## 机制原理

| 方案 | 依赖怎么注入 | ① 数据路径（值怎么到组件） | ② 通知机制（怎么触发重渲染） |
| --- | --- | --- | --- |
| **A. Context + useReducer** | `<Ctx.Provider value={{state,dispatch}}>`——**state 本身就在 Context 值里** | `useContext` 直接返回 | **Context 值引用变化** → 自动重渲染所有 consumer（①②耦合，故粗粒度） |
| **B. Zustand** | 无注入：`import` 模块单例 | 订阅后 `getSnapshot` 现读 + selector | `useSyncExternalStore`（v4 用 WithSelector shim，v5 用 React 内置） |
| **C. Redux（react-redux）** | `<Provider>` 注入 **store 稳定引用** | `useSelector` → `getSnapshot` 现读 + selector | `useSyncExternalStore(WithSelector)`（v8 / v9） |
| **D. Jotai** | StoreContext 注入 **store 稳定引用**（无 Provider 时取默认全局 store） | `useAtom` → 读 atom 当前值 |  **`useReducer` + `store.sub()`** 自行触发，**非** `useSyncExternalStore` |
| **E. Valtio** | 无注入：`import` 模块级 proxy | `useSnapshot` → 订阅后 `getSnapshot` 现读 | `useSyncExternalStore` |

**关键结论**：

1. **「需 Provider」的本质** = 这个库通过 **React 树**传依赖，还是通过 **ES module 单例**传依赖。
2. **Context 里装什么决定它的角色**：装**稳定引用** → 只做注入（Redux / Jotai）；装**会变的状态** → 兼作更新通道（方案 A）；两者都装 → React Router（非状态库）。
3. **只有方案 A 把「变化的 state」放进 Context 值**，所以粗粒度、画布会卡；其余四者都把变化移出 Context，改由订阅送达。
4. **`useSyncExternalStore(subscribe, getSnapshot)` 天生把两件事分开**：`subscribe` = ②通知，`getSnapshot` = ①数据路径；细粒度来自 selector + `Object.is` bail-out。
5. **Redux 的 store 通常也是模块单例**，但 react-redux **刻意不让你直接 import**，而要求经 Provider 注入——换取 scope 隔离 / SSR / 测试可替换。这与 Zustand「直接 import」是**设计取舍，不是能力差异**。
6. **全局 store 不是 React 自带的**，是库（jotai 的 `defaultStore`）或你（`create()` / `proxy()`）建的模块单例。

## useSyncExternalStore

### 作用

- 将外部的store变化同步到react中

## 简化版源码

```tsx

/* ═══════════════════════════════════════════════════════════
 * useSyncExternalStore 完整流程
 * ═══════════════════════════════════════════════════════════ */


/* ───────── ① 外部 store：纯 JS，活在 React 之外 ───────── */

const createStore = (initial) => {
  let state = initial                  // 纯 JS 变量，React 感知不到
  const listeners = new Set()

  return {
    getSnapshot: () => state,          // 【数据路径】读当前值
    subscribe: (fn) => {               // 【通知】注册回调
      listeners.add(fn)
      return () => listeners.delete(fn)
    },
    setState: (next) => {
      state = next                     // 数据真的变了
      listeners.forEach((fn) => fn())  // 广播通知（很"粗"，所有订阅者都收到）
    },
  }
}

const store = createStore({ count: 0, theme: 'light' })


/* ───────── ② 组件里怎么用 ───────── */

const Counter = () => {
  const count = useSyncExternalStore(
    store.subscribe,                   // 【② 通知】
    () => store.getSnapshot().count    // 【① 数据路径 + selector】只关心 count
  )
  return <div>{count}</div>
}

const ThemeLabel = () => {
  const theme = useSyncExternalStore(
    store.subscribe,
    () => store.getSnapshot().theme    // 只关心 theme
  )
  return <div>{theme}</div>
}


/* ───────── ③ React 内部：Hook 的两个分支 ───────── */

// 首次渲染 → mount 分支
function mountSyncExternalStore(subscribe, getSnapshot, getServerSnapshot) {
  const fiber = currentlyRenderingFiber
  const hook = mountWorkInProgressHook()

  const nextSnapshot = getSnapshot()        // 读当前值
  hook.memoizedState = nextSnapshot         // 存进缓存
  const inst = { value: nextSnapshot, getSnapshot }
  hook.queue = inst

  mountEffect(subscribeToStore.bind(null, fiber, inst, subscribe), [subscribe])  // 订阅

  // 两道检查都要登记——mount 与 update 皆然，不是只有首次渲染
  pushSimpleEffect(HasEffect | Passive, { destroy: undefined },                 // ← 提交后检查
    updateStoreInstance.bind(null, fiber, inst, nextSnapshot, getSnapshot), null)
  pushStoreConsistencyCheck(fiber, getSnapshot, nextSnapshot)                   // ← 提交前检查（防撕裂）
  return nextSnapshot
}

// 重渲染 → update 分支
function updateSyncExternalStore(subscribe, getSnapshot, getServerSnapshot) {
  const fiber = currentlyRenderingFiber
  const hook = updateWorkInProgressHook()

  const nextSnapshot = getSnapshot()        // 再读一次
  const changed = !objectIs(hook.memoizedState, nextSnapshot)
  if (changed) {
    hook.memoizedState = nextSnapshot       // ← 缓存被刷新（"nextSnapshot 更新"在这一行）
    didReceiveUpdate = true
  }
  updateEffectImpl(2048, Passive, subscribeToStore.bind(null, fiber, hook.queue, subscribe), [subscribe])

  // 只有"值确实变了"才需要跑检查；值没变 = bail out，两道都跳过
  const needsCheck = changed || hook.queue.getSnapshot !== getSnapshot
  pushSimpleEffect(needsCheck ? HasEffect | Passive : Passive, { destroy: undefined },   // ← 提交后检查
    updateStoreInstance.bind(null, fiber, hook.queue, nextSnapshot, getSnapshot), null)
  if (needsCheck && !isHydrating && 0 === (renderLanes & 127))   // 同步/高优先级渲染不会撕裂，跳过登记
    pushStoreConsistencyCheck(fiber, getSnapshot, nextSnapshot)  // ← 提交前检查（防撕裂）
  return nextSnapshot                       // 组件用这个值渲染
}


/* ───────── ④ 订阅、比较、调度 ───────── */

function subscribeToStore(fiber, inst, subscribe) {
  // 把 React 的回调交给你的 store；store 一变就执行这里
  return subscribe(function () {
    checkIfSnapshotChanged(inst) && forceStoreRerender(fiber)
  })
}

function checkIfSnapshotChanged(inst) {
  const nextValue = inst.getSnapshot()      // 重新读一次
  return !objectIs(inst.value, nextValue)   // 与缓存比：相同 → false → 整条链路静默跳过
}

function forceStoreRerender(fiber) {
  const root = enqueueConcurrentRenderForLane(fiber, 2)
  if (root !== null) scheduleUpdateOnFiber(root, fiber, 2)   // 调度 React 重渲染
}


/* ───────── ⑤ 提交后：对齐缓存 + 再查一次 ───────── */

function updateStoreInstance(fiber, inst, nextSnapshot, getSnapshot) {
  inst.value = nextSnapshot                 // 比较基准刷新为本次渲染的快照
  inst.getSnapshot = getSnapshot
  checkIfSnapshotChanged(inst) && forceStoreRerender(fiber)   // 渲染期间又变了 → 再渲染
}


/* ───────── ⑥ 防撕裂（tearing）登记 ───────── */

function pushStoreConsistencyCheck(fiber, getSnapshot, renderedSnapshot) {
  fiber.flags |= 16384
  const check = { getSnapshot, value: renderedSnapshot }
  const queue = (fiber.updateQueue ??= createFunctionComponentUpdateQueue())
  queue.stores = [check]
  // render 结束产出 finishedWork 后、commit 之前，由 isRenderConsistentWithExternalStores 复查：
  // objectIs(getSnapshot(), renderedSnapshot) 不一致 → 整次渲染作废，以同步优先级重做（防撕裂）
}


/* ═══════════════════════════════════════════════════════════
 * 一次变更的完整时序（store.setState({ count: 5 })）
 * ═══════════════════════════════════════════════════════════

  ┌ ① store 内部：state.count 0 → 5（纯 JS，React 看不见）
  │     此刻 getSnapshot() 会返回 5，但 inst.value / hook.memoizedState 还是 0
  ↓
  ┌ ② listeners.forEach(fn => fn())  —— 广播，两个组件都收到
  │     ├─ Counter:   checkIfSnapshotChanged → getSnapshot().count = 5
  │     │             objectIs(0, 5) === false → true → forceStoreRerender ✅ 重渲染
  │     └─ ThemeLabel: checkIfSnapshotChanged → getSnapshot().theme = 'light'
  │                   objectIs('light','light') === true → false → 跳过 ❌ 不重渲染
  ↓                   ↑ 这就是"细粒度"的来源：selector + Object.is bail-out
  ┌ ③ 重渲染 → updateSyncExternalStore
  │     nextSnapshot = getSnapshot() → 5
  │     与 hook.memoizedState(0) 比较 → 不同 → hook.memoizedState = 5
  │     返回 5，组件用新值渲染
  │     同时登记两道检查（mount 与 update 都会登记，不是只有首次渲染）：
  │       · pushStoreConsistencyCheck              → 提交前
  │       · pushSimpleEffect(updateStoreInstance)  → 提交后
  ↓
  ┌ ④ 提交前 → isRenderConsistentWithExternalStores(finishedWork)
  │     复查 objectIs(getSnapshot(), renderedSnapshot)
  │     不一致 → 整次渲染作废，以同步优先级重做一次（防撕裂）
  ↓
  ┌ ⑤ commit（真正落地到 DOM）
  ↓
  └ ⑥ 提交后 → updateStoreInstance
        inst.value = 5（比较基准刷新，下次以 5 为准）
        再 checkIfSnapshotChanged 一次：提交后又变 → 再渲染

  注：值没变的渲染（bail out）不会登记上述两道检查。

 * ═══════════════════════════════════════════════════════════ */


```
