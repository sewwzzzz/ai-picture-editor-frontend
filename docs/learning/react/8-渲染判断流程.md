# React 渲染判断流程(面试回答版 · React 19)

> 用法:每个问题先答**加粗的那一句结论**,讲完再展开原理。面试官一般就要前半句。

---

## 0. 总纲一句话

**React 判断要不要重渲染,是「自下标记、自上判断」**:更新先自下往上记 lane 到根,渲染时再从根往下逐个 fiber 问「你到底有没有变化」,没变化的整棵子树跳掉。**重渲染 ≠ 改 DOM**,DOM 由 commit 阶段决定。

---

## 1. 触发源

**更新只能从三个地方来:自身 setState/dispatch、根级 render、外部 store;子组件拿到新 props 不算触发源。**

- `setState` / `forceUpdate`(类)、`useState` / `useReducer` dispatch(函数)→ 入队列。
- Context Provider `value` 变 → 消费者才会被标 lane。
- `root.render()`、`useSyncExternalStore`(zustand / redux 底层)、并发重调度。
- 「子组件收到新 props」是**父组件渲染的结果**,不是独立触发源——这句话面试是加分项。  

---

## 2. 调度阶段

> ① Action → 队列(自动批处理 + eagerState)
> ② 自下往上标记(后续自上向下执行时判断)
> ③ 汇报到根 + 优先级判断

- ① 同一个事件里的多次 dispatch 会**自动批处理**(React 18+ 全环境)。eagerState:自身与 alternate 都无 lane、且渲染过 reducer 时,React 提前算 newState,`Object.is` 相等则**直接不调度**。
- ② `markUpdateLaneFromFiberToRoot`:自己记 `lanes`,沿途祖先记 `childLanes`(「我下面有人要更新」),root 记 `pendingLanes`。**这一步只做标记,不做判断。**
- ③ `ensureRootIsScheduled`:按优先级走 `performSyncWorkOnRoot` 或 `performConcurrentWorkOnRoot`。

---

## 3. 渲染阶段:每个 fiber 要过两道关卡

> 拿「安检」类比:**第一道粗筛(比引用),第二道精筛(比内容)。**

```
current === null(挂载)→ 必渲染

更新 fiber:
└─ 粗筛(beginWork 三问): props引用没变 AND 无 lane AND context 没变
     ├─ 全成立 → bailoutOnAlreadyFinishedWork(跳过,出口 1)
     └─ 否则 → 进 tag 分支(精筛)
          ├─ memo:      props内容相等 AND 无 lane AND context 没变
          │               ├─ 成立 → 跳过(出口 2)
          │               └─ 否则 → 渲染
          ├─ 类组件:    forceUpdate > SCU(比 props+state) > PureComponent 浅比 > 默认更新
          │             OR context 变了(不看 lane:自己的 setState 允许被 SCU 否决)
          │               ├─ 结果 false → 跳过(不 render / 不改 DOM / 不 cDU,但 state 已写回)
          │               └─ 结果 true  → 渲染
          └─ 普通函数组件: 无第二道 → 函数体必跑
                            └─ 跑完确实无变化 → 回滚改动 + 跳过子节点(但函数已执行过)
```

两条要点:
- **出口 1 与出口 2 是「或」**:任一成立就跳过;粗筛过了根本不进第二道。
- **精筛是粗筛失败后的「补考」**:只把 props 那条从「比引用」放宽成「比内容」,另两条(自身无 lane、context 没变)照旧——所以 **context / state 一变就铁定拦不住**。

#### 类组件那条分支展开(`>` 表示优先级 / 短路)

```js
if (forceUpdate)                         渲染 = true      // 强制,跳过 SCU
else if (instance.shouldComponentUpdate) 渲染 = SCU(...)   // 用你的返回值
else if (PureComponent)                  渲染 = !shallowEqual(props) || !shallowEqual(state)
else                                     渲染 = true       // 普通 Component 默认必渲染

// 最后还要 OR 一道:
渲染 = (上面一串) || checkIfContextChanged(dependencies)
```

- `forceUpdate` 是无条件渲染,**根本不调用 SCU**——它和 `setState` 的核心区别就在这。
- `PureComponent` = 类组件版的 `memo`,自带 props/state 浅比较;**和自定义 SCU 同时写会被 React 警告**(既然继承 PureComponent 就不要再写 SCU)。
- **context 变了照样渲染**,即便 SCU 返回 false——这是类组件的「真·硬绕过」,和 memo 那边"不 return"的机制不一样。
- **注意这里 OR 的只有 context,没有 lane**——故意的:lane 的职责是「能不能进第二道」(第一道已查过),进了之后由 SCU 说了算;**自己的 `setState` 产生的 lane 必须允许被 SCU 否决**,否则 SCU 就永远失效、失去意义。而 context 不能被否决:组件确实订阅了它,值变了还拦着不渲染就会显示旧数据(bug)。
- 对比 memo 用的 `checkScheduledUpdateOrContext`(**lane + context 都看**):函数组件没有"否决自己 state"的语义,hook state 变了就必渲染,所以 lane 一律放行,最终由 hook 比较决定。

### 跳过之后,跳到什么程度?
```
bailoutOnAlreadyFinishedWork
├─ 子树没有本轮 lane → 整棵子树跳过
└─ 子树还有 lane     → 当前组件不执行,但继续往下找那个要更新的节点
```
**父组件 bailout ≠ 子组件一定不更新。** 这句是高频追问。

## 4. 面试问答

### Q1:父组件重渲染,子组件一定会重渲染吗?
**普通子组件基本上会;但「它会不会因为 props 变化而渲染」是结果,不是原因。**

父一渲染就给子造了新 props 对象,引用必变 → 第一道答「是」 → 普通函数组件没有第二道 → **函数体一定执行**。
想拦下来只能靠:memo、以及在更上层就整棵 bailout。

### Q2:`memo` 是怎么做到跳过的?
**它是第二道关卡:第一道只比引用必输,`memo` 再比一次内容。**

条件:`shallowEqual(prevProps, nextProps)` 且 ref、type 都没变。相等就走 `bailoutOnAlreadyFinishedWork`。
但两个前提要补:**自己 state 变了、或读的 context 变了,照样渲染**——这两种情况 fiber 已经被打了 lane,`memo` 拦不住。

### Q3:函数组件有没有类似 `shouldComponentUpdate` 的兜底?
**没有。进入 `updateFunctionComponent` 就意味着函数体一定执行。**

这是最容易说错的一题。19 的实现是:**先无条件执行函数体**(`renderWithHooks`),跑完才回头看有没有真的变化;没变化才回收改动、跳过子节点协调。
换句话说 React 是「先斩后奏」,**函数组件不存在「渲染前跳过」**。真正能让它不跑的只有两条:上一层的 early bailout,或者包 `memo`。

> 顺带厘清概念:**第一道比的是引用**(`oldProps !== newProps`,和 `Object.is` 对对象等价,不拆壳);**`memo` 默认 compare 是 `shallowEqual`(浅比较,只拆第一层、每个值再用 `Object.is` 收口)**。所以 `memo` 拦得住 `{name:'a'}` vs `{name:'a'}`,但拦不住 `{user:{id:1}}` vs `{user:{id:1}}`(嵌套对象引用不同)。`Object.is` 最浅——浅到一层都不拆。

### Q4:类组件 `shouldComponentUpdate` 返回 false 会怎么样?
**不执行 render、不提交 DOM、不调 `componentDidUpdate`;但 `props/state/context` 已经写回实例了。**

所以 instance 上的状态是最新的,只是没渲染。补充两点:
- `forceUpdate` 优先级最高,**绕过 SCU**;
- **context 变化也会被 OR 进判定**,同样绕过 SCU。

### Q5:Context 变了为什么会绕过 memo?
**不是跳过 memo 那一道,而是废掉了 memo 的 bailout 前提:`memo` 只在「props 相等 且 自身无 lane 且 context 没变」时才跳过。**

19 的机制:Provider 更新后**不再自己比较 value**(18 会),照常往下协调;消费者拿 `Object.is` 比「当前值 vs 上次记住的值」。不一样 → 完整链路是:

1. **第一道**:`checkScheduledUpdateOrContext` 为真 → 不 early bailout → 照样进 tag 分支。
2. **第二道(memo)**:`shallowEqual` **会通过**(props 确实没变),但 bailout 前还要再查一次 `checkScheduledUpdateOrContext`;context 变了 → 条件不成立 → **不 return**,继续落到 `updateFunctionComponent` → 函数体执行。
3. 函数体跑完还有保险:context 依赖变了会置 `didReceiveUpdate = true`,避免被末尾的回滚拦下,最终正常 reconcile + commit。

所以 `shallowEqual` 相等没用,它只是 bailout 的**必要条件之一**。类组件才是真硬绕过:判定是 `checkShouldComponentUpdate(...) || checkIfContextChanged(...)`,context 直接 OR 进结果,`sCU` 返回 false 也没用。
结论:`<Provider value={{...}}>` 传字面量,每次都是新对象 → **每次都全量向下传播**,必须用 `useMemo` 包 value。这是 Context 性能问题的首因。

> `memo` 的 `shallowEqual` 和 Context 的 `Object.is` 别混:**`Object.is` 比的是引用、一层都不拆**;`shallowEqual` 只拆第一层。Context 直接用 `Object.is` 比整个 value 对象,所以只要每次是 `new` 出来的对象就一定不相等,跟里面内容一不一样无关。

### Q6:`setState` 传相同的值,会重渲染吗?
**多数时候不会,但要分清两级拦截。**

- 一级(eagerState):dispatch 时若 fiber 与 alternate 都无 lane,提前算值与旧值 `Object.is` 相等 → **连调度都不发起**。对象/数组每次新引用必不相等,享受不到这个优化。
- 二级:就算调度了,render 出来 state 没变、又没有其它变化,仍会在 `updateFunctionComponent` 末尾被拦下。

### Q7:重渲染一定改 DOM 吗?
**不一定。渲染只是跑一遍组件 + 协调;改不改 DOM 由 commit 决定。**

completeWork 阶段对新旧子节点做 diff,输出没变就打不上 flag,commit 阶段一个 DOM 操作都不会做。所以「组件重跑」的成本通常只是几次函数调用,不该恐慌。

### Q8:StrictMode 下我的组件为什么跑了两次?并发还能丢弃 render?
**都是预期行为,所以不能用「函数执行次数」当渲染次数,得看 Profiler。**

DEV StrictMode 刻意双调用来找副作用;并发模式下低优先级 render 被打断后会被**整段丢弃重来**。结论:组件必须是纯函数,别把副作用写在函数体里。

### Q9:`key` 变了会怎样?
**卸载重建,state 丢失——这不是重渲染。**

同 key 同 type 才复用 fiber;任何一个变了都是删除 + 新建。所以 key 千万别用数组下标(列表删除时会错位复用)。

### Q10:怎么让子树少渲染?(综合方案)
1. Provider 的 `value` 用 `useMemo`(最常见收益);
2. 真正昂贵的子树包 `memo`,并保证 props 引用稳(配合 `useCallback` / `useMemo`);
3. 外部 store 用细 selector 订阅(默认 `Object.is`,要按内容比就用 zustand 的 `useShallow`);
4. 状态尽量**往下放**,让更新源更靠近真正需要它的组件。
最后补一句兜底:**`useMemo`/`useCallback` 本身不是跳过机制**,它们只是稳引用,服务于 memo 比较、`useEffect` 依赖、`useMemo` 链;没有下游消费的话,单写是零收益。

## 5. 速查表

| 场景 | 重渲染? |
| --- | --- |
| 父渲染 + 普通子组件 | 通常**是** |
| 父渲染 + `memo` 子,props 浅相等,无 state/context | **否** |
| `PureComponent`,props/state 浅相等 | **否** |
| `shouldComponentUpdate` 返回 false | **否**(但 state 已写回实例) |
| `setState` 相同值且无其他更新 | **否**(eagerState 直接不调度) |
| Context value 变化 | 消费者**是**(绕 memo/SCU) |
| `forceUpdate` | **是** |
| key 变化 | 卸载重建,非重渲染 |
| 组件重跑但输出未变 | render 发生,commit **不改 DOM** |

## 6. 对照本项目(Toast)

```
push() → 新数组 → useSyncExternalStore 通知
  → selector 输出 Object.is 不等 → ToastHost 打 lane → 调度
  → beginWork(ToastHost): 有 lane → 不 bailout → 重跑
  → .map → reconcileChildren 按 key 复用
  → beginWork(ToastCard): props 新对象 → 非 memo → 函数体必跑
  → completeWork diff: 输出未变 → 无 DOM flag
  → commit: DOM 不动;effect 依赖稳 → 定时器不重置
```

结论:新 toast 进来会让**所有** ToastCard 重跑(没包 memo 就是会跑,见 Q3),但 DOM 不动、状态不丢、定时器不重置——代价是几次廉价函数调用,**无需优化**;真在意就给 ToastCard 包一层 `memo`,只有新增那张会渲染。

## 个人总结（建议先看）

### 流程简计  

触发源 -> 标记（自下而上） -> 重渲染（自上而下） -> 改DOM

### 组件

#### 类型

1. 类组件 <tag:ClassComponent>
2. 函数组件 <tag:FunctionComponent>
3. React.memo包裹的函数 <tag:SimpleMemoComponent>/<tag:MemoComponent>

> 推荐使用函数组件，唯一缺少的是类的捕获子树在渲染期间抛出错误的边界处理。

#### 差异

1. 渲染机制

2. this.state + setState(浅合并一层) vs useState(替换)

- 类组件每次读的属性是当前最新值，this是引用，访问时才读取的属性

- 函数组件每次读的属性是本次渲染的快照(闭包)，不一定是最新

3. 生命周期 vs Hooks

4. this 与 普通变量

5. 错误边界

### 单个步骤

#### 触发源

- 自身 setState/dispatch、根级 render、外部 store

#### 渠道

- props、context

#### 标记

- lanes -> childLanes ...

#### 重渲染

- 一轮粗筛 + 二轮tag判断

- tag=memo时，只是强化了一个判断：props引用 -> 浅比较

- tag=类时，第二道比的是 props+state 的**内容**（SCU / PureComponent），再 OR context，**不看 lane**

> 外部state传入 + 内部自身state变化
