# 传输层统一处理

## 决策视角（选型）

> **先划清层次**：**传输层 ≠ 服务端状态层**。传输层管「怎么把 HTTP 发出去」；TanStack Query 管「服务端数据怎么存、何时失效、并发如何协调」，且它**自己不发请求**，只调用你给的 `queryFn`。二者是**叠加**关系（M0 只建传输层，M1+ 叠加服务端状态层），**不是二选一**。

| 方案 | 定位 | 上传进度 | 4xx/5xx 自动抛错 | 超时 / 取消 | 统一错误 + 401 | 体积 | 本项目 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **A. axios** | 传输层 | ✅ `onUploadProgress` | ✅ 非 2xx 自动 reject | ✅ `timeout` / `AbortController` | ✅ 拦截器一等场景 | ~13KB（gzip ~5KB） | ✅ **推荐** |
| **B. 原生 fetch 自建封装** | 传输层 | ❌ 几乎不可行 | ❌ 需自行判 `res.ok` | △ `AbortSignal.timeout` 自己接 | △ 拦截模式自己搭 | 0 | 中：省依赖但有硬伤 |
| **C. ky / ofetch** | 传输层 | ❌ 同 fetch 限制 | ✅ | ✅ | ✅ hooks | ~4KB | 低：生态小、熟度低 |
| **D. TanStack Query** | **服务端状态层**（非传输层） | — | — | — | — | ~13KB | 非本层候选，M1+ 叠加 |

## 方案（单选）

- [x] axios
- [ ] 原生 fetch 自建封装
- [ ] ky / ofetch
- [ ] TanStack Query（注：非本层候选，是 M1+ 叠加的服务端状态层）

> **单选理由**：
> 1. **存在能力差异，不只是 DX**：AI 修图必然上传原图（M2/M3），axios 基于 XHR 提供 `onUploadProgress` 上传进度；原生 fetch 的流式上传（`duplex: 'half'`）浏览器支持不全，进度基本不可行——这是 fetch 方案补不上的硬伤。
> 2. **与参考规范一致**：主参考 bulletproof-react 的 `lib/api-client.ts` 即 axios 实例 + 响应拦截器，与选 React Router、Zustand 同一判断逻辑。
> 3. **命中任务需求**：本任务就是「统一处理请求错误与认证失败」——响应拦截器统一归类错误、统一处理 401，正是该需求的一等解法，样板最省、最不易漏。
> 4. **开箱能力省样板**：非 2xx 自动 reject、`timeout`、请求取消、自动 JSON 解析皆内置；fetch 需逐一自建，最终等于手写一个 mini-axios。
> 5. **生态与排障**：最成熟、社区最大，面试与协作语境下最通用。
>
> **不选 fetch 自建**：上传进度缺失是硬伤；且错误分类、`AbortSignal.timeout`、拦截模式都要自己写，省下的 ~5KB gzip 换来更多自维护代码与出错面。
>
> **不选 ky / ofetch**：同样基于 fetch，无上传进度；生态与团队熟度明显低于 axios。
>
> **TanStack Query 的定位**：它是**服务端状态层**（缓存只是其核心机制之一，此外还管失效、竞态、重试、后台刷新、乐观更新），需 axios 提供的 fetcher 作为底层。M0 只建传输层；M1 起服务端状态出现后再叠加，职责不重叠。
>
> **体积代价评估**：~5KB gzip 换上传进度 + 零样板错误处理；本项目体积大头在画布（Konva），此代价可忽略。

## 落地约定（M0）

- 落位：`src/lib/api-client.ts`（axios 实例 + 响应拦截器），`baseURL` 取自 `src/config/`——符合目录规范「有状态 / 需初始化 → `lib/`」。
- 统一错误：拦截器把错误归一为项目内 `ApiError`（网络错误 / HTTP 错误 / 业务错误），调用方无需各自 `try/catch` 分类。
- 401 边界：**M0 只识别并预留钩子**（无登录页，不做后续页面），不实现跳转；M1 接入认证后在该钩子内补重定向。
- 与 Cookie 同源：认证用 httpOnly Cookie（后端已定），`baseURL` 走 `/api` 由 Vite 代理转发保持同源，Cookie 自动携带——对应 ROADMAP 的复盘点「代理为何与 Cookie 同源相关」。
- 范围约束：仅接入 `/api/health`，不写后续业务接口。

## 实现（M0）

### 依赖

```
axios            ^1   # 传输层：请求实例 + 拦截器
```

### 文件

```
src/
├─ config/
│  └─ env.ts           # 全局配置唯一出口：API 前缀 / 请求超时（读环境变量并给出默认值）
├─ lib/
│  ├─ api-client.ts    # axios 实例 + ApiError 归一 + 401 钩子 + 响应拦截器
│  └─ health.ts        # GET /health（M0 唯一接入的接口）
├─ vite-env.d.ts       # import.meta.env 的类型声明（自定义 VITE_* 变量）
vite.config.ts         # server.proxy：/api 转发后端，保持同源
.env.example           # 环境变量样例：代理目标 / API 前缀 / 超时
```

### 错误归一

响应拦截器把一切失败统一转成项目内的 `ApiError`，字段为 `kind` / `message` / `status` / `code` / `payload`，调用方 `catch` 到的是**同一种东西**，无需各自做 `res.ok` 判断或错误分类。

`kind` 的判定：

| kind | 触发条件 | message |
| --- | --- | --- |
| `network` | 无响应（含超时 `ECONNABORTED`） | 「请求超时」或「网络异常」 |
| `http` | 有响应且非 `success:false` 信封的 4xx/5xx | 「请求失败（HTTP 状态码）」 |
| `business` | HTTP 2xx 但后端信封 `success === false` | 取后端的 message，缺省「业务处理失败」 |
| `aborted` | `AbortController` 取消（`ERR_CANCELED`） | 「请求已取消」 |

### 401 边界（M0 只预留）

- 拦截器识别到 `status === 401` 时，调用**外部注入的钩子**（默认无处理器，静默放过）。
- M0 没有登录页，钩子留空不做跳转；M1 接入认证后调用 `setUnauthorizedHandler` 注入重定向即可，**无需改动拦截器**。

### 同源与 Cookie

- `apiClient` 的 `baseURL` 默认 `/api`，与页面同源，因此 httpOnly Cookie **自动携带**，不需要显式开启 `withCredentials`。
- `vite.config.ts` 配 `server.proxy` 把 `/api` 转发到后端；目标地址从 `VITE_PROXY_TARGET` 读取，默认 `http://localhost:8080`（后端代码尚未落地，端口待对齐后可在 `.env` 覆盖）。

### 校验

- `npm run typecheck` ✓
- `npm run build` ✓
- 运行时冒烟：需后端 `/api/health` 就绪后，由 UI 或临时脚本调用 `getHealth()` 验证代理与 Cookie 链路。

### 关键约定

1. **环境变量只从 `config/env.ts` 出口读取**，其余代码不得直接碰 `import.meta.env`。
2. **只从 `lib/api-client.ts` 导出实例发请求**，不在组件里直接 `axios.get`；业务接口后续进 `features/<name>/api/`。
3. **传输层不碰服务端状态**：缓存、失效、重试交给 M1+ 叠加的 TanStack Query，本层只负责"把请求发出去并把错误归一"。
4. **调用方按 `kind` 分派 UI**，不按 `status` 逐条写 if——这样后端换错误码格式时只改拦截器一处。
