### 路径别名 `@/*` → `src/*`

**必须两处成对配置**，只配一边会导致 TS 与 Vite 行为不一致：

| 解析器 | 配置文件 | 内容 |
| --- | --- | --- |
| TypeScript（编辑器提示、`tsc`） | `tsconfig.app.json` | `"baseUrl": "."`、`"paths": { "@/*": ["./src/*"] }` |
| Vite（`dev` / `build` 打包） | `vite.config.ts` | `resolve.alias` + `fileURLToPath(new URL('./src', import.meta.url))` |

`@types/node` 是 `vite.config.ts` 里 `import ... from 'node:url'` 的类型依赖，缺它 `tsc -b` 会报 `Cannot find module 'node:url'`。

## 搭建路由框架

### 路由组织范式（单选）

- [ ] pages/（文件式：文件名即路径，需 `vite-plugin-pages` 等扫描插件）
- [x] routes/（配置式：显式路由表，路径与组件映射手写）

> **单选理由**：本项目需要**动态参数**（如 `/editor/:taskId`）、**嵌套布局**（编辑器外壳 + 子页面）、**权限守卫**（未登录拦截），这类复杂路由用显式配置表表达最直观、可控性最强；而 `pages/` 文件式靠隐式约定，处理嵌套与守卫时受限、且需额外引入构建插件。故选择 `routes/`，并与目录规范中「`routes/` 与 `pages/` 二选一，不得共存」的铁律一致。

### 方案（单选）

- [x] React Router v7
- [ ] TanStack Router

> **单选理由**：
> 1. **需求全覆盖**：动态参数、嵌套布局（`Outlet`）、权限守卫（loader / 守卫组件），RR v7 均原生一等支持，正是选 `routes/` 的三个动因。
> 2. **契合目录结构**：`createBrowserRouter` + `src/routes/` + `src/app/router.tsx` 天然落地，不改动 Vite 构建管线。
> 3. **生态与参考一致**：最成熟、社区最大；本项目主参考 bulletproof-react 亦采用 React Router。
>
> **不选 TanStack**：其优势是 DX（编译期类型安全、search params 原生校验）而非能力——RR v7 用 `useSearchParams` 同样能同步 URL 状态，只是需手写类型推断与校验。当前该红利非阻塞；且 TanStack 两种组织方式均有代价：**代码式**样板明显多于 RR v7；**文件式**需引入插件做 codegen、且路径由文件名决定（实质 `pages/` 风格），与 `routes/` 配置式约定冲突。
>
> **重新评估时机**：URL 参数 ≥ 8 个且被 ≥ 4 个组件读取，或首次出现因默认值 / 布尔解析不一致导致的状态 bug——届时 TanStack 的集中 schema 能显著减少类型漂移。
>
> 注：两方案能力等价（均可配置式路由、均可同步 URL 状态），差异仅在**类型安全、校验机制与样板量**。

### 实现（M0）

- 依赖：`react-router-dom@7.18.4`（v7，类型自包含，无需 `@types`）
- 文件：
  - `src/app/router.tsx` —— `createBrowserRouter` 生成的路由实例（根布局 + `/` 首页），是 router 唯一出处
  - `src/routes/RootLayout.tsx` —— 根布局，渲染 `<Outlet />`，后续嵌套页面落在此
  - `src/routes/HomePage.tsx` —— 占位首页（`index` 路由）
  - `src/app/App.tsx` —— 渲染 `<RouterProvider router={router} />`
- 校验：`tsc -b` ✓、`vite build` ✓（43 modules）
- 关键约定：路由实例只放 `src/app/router.tsx`；页面组件放 `src/routes/`；组件内跳转用 `Link` / `useNavigate`，不在页面里写路由表。

## 搭建状态管理框架

**决策视角（选型）**

| 方案 | 需 Provider | 需 Context | store 从哪来 | React 外可读 | 更新粒度 | 本项目 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. Context + useReducer** | ✅ 必须 | ✅（它就是 Context 本身） | `useReducer` 建在 Provider 组件内，随 Provider 生灭 | ❌ 取不到 | ❌ 粗：全体 consumer 一起重渲染 | ❌ 排除（画布高频更新会卡） |
| **B. Zustand** | ❌ | ❌ | 你 `create()` 的**模块级单例** | ✅ `useAppStore.getState()` | ✅ 选择器级（+ transient 可绕过 React） | ✅ **推荐** |
| **C. Redux Toolkit** | ✅ `<Provider store>` | ✅（ReactReduxContext 传 store 引用） | 你 `configureStore()` 建（**通常也是模块单例**），但**经 Provider 注入** | ✅ `store.getState()`（需先拿到引用） | ✅ 选择器级 | 中：样板重 |
| **D. Jotai** | ❌（不写时回落全局 store） | ✅（内部 StoreContext；无 Provider 时取 jotai 自带 `defaultStore`） | jotai 模块 import 时自建 `defaultStore` 单例；也可 `createStore()` 自建 | ✅ `getDefaultStore().get(atom)` | ✅ 原子级 | 高：编辑器场景也顺 |
| **E. Valtio** | ❌（无 Provider） | ❌ | 你 `proxy()` 的**模块级单例** | ✅ `snapshot(state)` / 直接读 proxy | ✅ 代理追踪级 | 高：画布可变对象友好 |

> 注：B / E 标 ❌ 指「**默认不需要**」。如需 SSR / 多实例隔离，Zustand 可用 `createStore()` + 自包 Context（官方 pattern），不改变「默认零 Provider」的结论。

### 服务端状态（配套决策，M1+ 才需要）

| 方案 | 用途 | 本项目契合度 |
| --- | --- | --- |
| **TanStack Query** | fetch/ mutation 缓存 + SSE 订阅封装 | **高：推荐配套** |
| **手写在 Zustand** | 自己管理 `竞态/缓存/失效` | 低：重复造轮子、易出竞态 |
| **XState** | 把 M5 进度/M7 任务流写成状态机 | 中：复杂异步流可选，M0 不必 |

### 单选理由

1. **画布高频更新（M3 最大痛点）**：拖拽/绘制时每帧都在变，`Context` 会让整棵树重渲染直接卡死；Zustand 的 `useStore(selector)` 只订阅用到的字段，配合 transient 更新（`setState` 不触发 React 渲染、用 `subscribe` 直接喂给 Konva）能扛住。Jotai/Valtio 也行，但 Zustand 心智负担最低。

2. **工具注册表（M4）天然适配**：所有工具在一处定义、被工具栏/画布/属性面板多处消费——Zustand 的 `getState()` 还能在 React 之外（如 Konva 事件回调、SSE 监听器）直接读状态，这是 Context 做不到的。

3. **样板最少、与文档约定一致**：`app/store/` 放全局 store、`features/*/stores/` 放模块 store，Zustand 的 `create()` 一个函数就完事；无需 Provider 包裹，接入 `App.tsx` 零侵入。

4. **与 React 19 兼容、生态最大**：Zustand 是 bulletproof-react 推荐栈之一，社区方案多，踩坑可搜。

5. **服务端状态交给 TanStack Query**：M5 的 SSE 进度、M7/M8/M9 的接口数据，用 Query 的缓存/重试/失效开箱即用；SSE 用 `queryClient.setQueryData` 在 `onmessage` 里增量更新即可。这样 Zustand 只装"UI 真相"、Query 装"后端真相"，边界清晰。

**为什么不选 Redux Toolkit**：能力够但 slice/action/selector 样板在 13 个模块里会显著拖慢开发，本项目没有"强规范审计"诉求；**为什么 Jotai/Valtio 落选**：能力等价甚至某些点更优，但 Zustand 的"全局可读 + 无 Provider + 生态最大"综合最稳。

> 客户端：Zustand，服务端：TanStack Query

## 传输层统一处理

### 决策视角（选型）

> **先划清层次**：**传输层 ≠ 服务端状态层**。传输层管「怎么把 HTTP 发出去」；TanStack Query 管「服务端数据怎么存、何时失效、并发如何协调」，且它**自己不发请求**，只调用你给的 `queryFn`。二者是**叠加**关系（M0 只建传输层，M1+ 叠加服务端状态层），**不是二选一**。

| 方案 | 定位 | 上传进度 | 4xx/5xx 自动抛错 | 超时 / 取消 | 统一错误 + 401 | 体积 | 本项目 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **A. axios** | 传输层 | ✅ `onUploadProgress` | ✅ 非 2xx 自动 reject | ✅ `timeout` / `AbortController` | ✅ 拦截器一等场景 | ~13KB（gzip ~5KB） | ✅ **推荐** |
| **B. 原生 fetch 自建封装** | 传输层 | ❌ 几乎不可行 | ❌ 需自行判 `res.ok` | △ `AbortSignal.timeout` 自己接 | △ 拦截模式自己搭 | 0 | 中：省依赖但有硬伤 |
| **C. ky / ofetch** | 传输层 | ❌ 同 fetch 限制 | ✅ | ✅ | ✅ hooks | ~4KB | 低：生态小、熟度低 |
| **D. TanStack Query** | **服务端状态层**（非传输层） | — | — | — | — | ~13KB | 非本层候选，M1+ 叠加 |

### 方案（单选）

- [x] axios
- [ ] 原生 fetch 自建封装
- [ ] ky / ofetch
- [ ] TanStack Query（注：非本层候选，是 M1+ 叠加的服务端状态层）

> **单选理由**：
> 1. **存在能力差异，不只是 DX**：AI 修图必然上传原图（M2/M3），axios 基于 XHR 提供 `onUploadProgress` 上传进度；原生 fetch 的流式上传（`duplex: 'half'`）浏览器支持不全，进度基本不可行——这是 fetch 方案补不上的硬伤。
> 2. **与参考规范一致**：主参考 bulletproof-react 的 `lib/api-client.ts` 即 axios 实例 + 响应拦截器，与选 React Router、Zustand 同一判断逻辑。
> 3. **命中任务需求**：本任务就是「统一处理请求错误与认证失败」——响应拦截器统一归类错误、统一处理 401，正是该需求的一等解法，样板最省、最不易漏。
> 4. **开箱能力省样板**：非 2xx 自动 reject、`timeout`、请求取消、自动 JSON 解析皆内置；fetch 需逐一自建，最终等于手写一个 mini-axios。
> 5. **生态与排障**：最成熟、社区最大，面试与协作语境下最通用。
>
> **不选 fetch 自建**：上传进度缺失是硬伤；且错误分类、`AbortSignal.timeout`、拦截模式都要自己写，省下的 ~5KB gzip 换来更多自维护代码与出错面。
>
> **不选 ky / ofetch**：同样基于 fetch，无上传进度；生态与团队熟度明显低于 axios。
>
> **TanStack Query 的定位**：它是**服务端状态层**（缓存只是其核心机制之一，此外还管失效、竞态、重试、后台刷新、乐观更新），需 axios 提供的 fetcher 作为底层。M0 只建传输层；M1 起服务端状态出现后再叠加，职责不重叠。
>
> **体积代价评估**：~5KB gzip 换上传进度 + 零样板错误处理；本项目体积大头在画布（Konva），此代价可忽略。

### 落地约定（M0）

- 落位：`src/lib/api-client.ts`（axios 实例 + 响应拦截器），`baseURL` 取自 `src/config/`——符合目录规范「有状态 / 需初始化 → `lib/`」。
- 统一错误：拦截器把错误归一为项目内 `ApiError`（网络错误 / HTTP 错误 / 业务错误），调用方无需各自 `try/catch` 分类。
- 401 边界：**M0 只识别并预留钩子**（无登录页，不做后续页面），不实现跳转；M1 接入认证后在该钩子内补重定向。
- 与 Cookie 同源：认证用 httpOnly Cookie（后端已定），`baseURL` 走 `/api` 由 Vite 代理转发保持同源，Cookie 自动携带——对应 ROADMAP 的复盘点「代理为何与 Cookie 同源相关」。
- 范围约束：仅接入 `/api/health`，不写后续业务接口。
