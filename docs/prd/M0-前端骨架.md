## 验收标准（做到什么算完成）

- 正常路径：后端应用正常运行的情况下，开发者运行构建命令后，可以在本地浏览器看到页面，能完成简单主题切换、路由跳转。

- 异常路径：后端没有启动应用的情况下，本地浏览器会出现合适的错误提示，而不是仅展示空白页

## 复盘记录（实现完成后填写，不要边写边填）

### 差异清单

| 关注点 | 我的做法 | 原实现 | 类型 | 差异原因 / 谁更好 |
| --- | --- | --- | --- | --- |
| 传输层底座 | axios 实例 + 响应拦截器，失败一律归一成 `ApiError` | 原生 fetch 手写 `request<T>()` + `apiError()` | 取舍不同 | 我换来超时/取消/拦截器；原实现零依赖包体更小，且上传下载可复用同一错误构造函数（axios 路线要另写一套） |
| 错误分类维度 | `code`/`expected`/`retryable`/`fields` + 状态码映射表，UI 按 code 分派 | 只有 `status` + `message`，UI 直接显示后端文案 | 我更优 | 分类码让「能否重试 / 是否预期内」有机器依据；原实现只能靠文案或 status 散写 if |
| 网络失败与超时文案 | `NETWORK`/`TIMEOUT` 单独成类，给中文兜底文案 | fetch 失败抛 TypeError，`errorMessage()` 把它当 Error 返回 `Failed to fetch` | 我更优 | 原实现会把浏览器英文原始错误直接漏到界面上 |
| 超时与取消 | axios `timeout` 15s（可配）+ 把 `ERR_CANCELED` 识别为 `ABORTED` | 无超时，全项目 0 处 `signal` | 我更优 | 生成类长任务必须能取消；原实现的轮询/上传一旦卡住只能等浏览器默认超时 |
| 401 处理 | 拦截器 + `setUnauthorizedHandler` 全局钩子（M1 注入跳转，须排除 login/register） | 无全局钩子；`useCurrentUser` 把 401 当正常态（`retry:false` + `throwOnError:false`），由 `RequireAuth` 布局路由跳 `/auth` | 取舍不同 | 会话过期主动踢出我更优；「未登录是数据不是错误」的建模原实现更干净，且天然不需要 login/register 例外表 |
| 预期失败的查询 | 全局按 `ApiError.retryable` 退避重试（上限 2）；401/404/409/413/422（`retryable:false`）不再白跑第二次；Mutation `retry:false` | `/auth/me` 显式 `retry:false` + `staleTime:Infinity` | 漏项（已补漏） | 原漏：全局 `retry:1` 未区分，401/404 会白跑第二次；已在 `query-client.ts` 把 `retry` 改为函数、仅对 `retryable` 为真者重试，补漏完成 |
| 全局反馈通道 | `app/store/useToastStore.ts`（zustand store + `toast` 门面 + `notifyError`）+ `components/ui/Toast/Toast.tsx`（`ToastHost`，自动消失/退场动画/可挂撤销动作），`App.tsx` 挂载一次；mutation 的 `onError` 经 `notifyError` 统一走 L3 | zustand toast store + `ToastHost`（自动消失、退场动画、可挂撤销动作），所有 mutation 的 `onError` 统一 toast | 漏项（已补漏） | 原漏：骨架期没定「错误用什么载体」，M1 各页面会各写各的；已实现全局 Toast 通道，约定 L3（5xx/网络/超时）走 toast、L1/L2 内联（见 error-handling.md 第 6 节） |
| 错误展示落点 | 三类落点组件已定型：L1 `components/ui/InlineError`（422 字段级 / 413 上传 / 登录注册 401，可按 `field` 取文案）、L2 `components/ui/ErrorPanel`（409 / 子资源 404，带可选标题与重试动作）、L3 全局 Toast（见上一行）；字段文案提取在 `utils/errorFields.ts` | 三类落点已定型：表单内联红字（AuthPage/CreatePage）、页面级错误区（BatchPage）、全局 toast（mutation） | 漏项（已补漏） | 原漏：M0 只有 dev 健康面板一处，PRD 第 8 条要的「不同位置——表单/页面、不同场景——登录/未登录」没有方案；现三落点组件已就位，M1 的 AuthPage/CreatePage/BatchPage 直接消费即可 |
| 上传/下载的错误通道 | `api-client.ts` 导出 async 助手 `apiError(response, fallback)`：`readBody(data)` 识别 Blob 后 `await data.text()` + `JSON.parse` 提取 code/message，解析不出用 `fallback`；`buildApiError` 与 `toApiError` 共用分类逻辑，产出与 JSON 请求同构的 `ApiError`（上传的 JSON 错误响应也能复用） | `apiError(response, fallback)` 专供 fetch 上传下载复用，文案格式与 JSON 请求一致 | 漏项（已补漏） | 原漏：M0 只有 JSON 通道，`readMessage(response.data)` 假设已是解析好的对象，Blob 下载错误拿不到 code/fields 只能兜底文案；已在 `api-client.ts` 补齐 `apiError` 助手（`typeof Blob !== 'undefined'` 做环境防护），M1 的上传/下载在 catch 里直接调用即可 |
| 状态管理分工 | zustand（客户端 UI）+ react-query（服务端），`queryClient` 单例放 `lib/` 并集中配 staleTime/gcTime | 分工相同；`queryClient` 在 `main.tsx` 内联创建，只配了 retry / refetchOnWindowFocus | 我更优 | 默认策略集中一处，避免每个 hook 重复配一遍 |
| Provider 装配 | 单独一层 `app/providers.tsx`，`App.tsx` 只做装配 | `QueryClientProvider` 直接写在 `main.tsx` | 取舍不同 | 我预留了后续加 Theme/ErrorBoundary 的位置；原实现少一层间接，M0 阶段更直接 |
| 路由形态 | `createBrowserRouter` 模块级 router 实例（预留 loader / 懒加载） | `<BrowserRouter>` + 声明式 `<Routes>`，页面全部静态 import，0 处 lazy / errorElement | 取舍不同 | 我为后续路由级分割铺路；原实现更简单，代价是首屏 bundle 全量 |
| 路由兜底 | `app/router.tsx` 末尾挂载 `{ path: '*', element: <NotFoundPage /> }`，作为 `RootLayout` 的子路由（保外壳）；新增 `routes/NotFoundPage.tsx` + CSS Module，展示 404 文案与「返回首页」链接 | `<Route path="*">` → `Navigate to="/"`（静默重定向） | 漏项（已补漏） | 原漏：骨架期无兜底，M1 加完页面后随便输个 URL 就是白屏；已补 404 兜底路由。取舍：我选显式 404 页而非静默重定向——用户输错 URL 时应明确告知，而不是被悄悄送回首页；M1 新增路由都写在它前面即可 |
| 代码分割 | 无（M0 只有一页），但 dev 面板已跑通 `lazy + Suspense` 这套写法 | 全项目无 lazy | 我更优 | M1 加页面时可直接照搬 dev 面板的模式 |
| 主题切换 | light/dark：`data-theme` + localStorage + 系统偏好 + `index.html` 防 FOUC 内联脚本 | 不做主题切换，单一浅色主题（`--color-dark` 只是个颜色名，不是暗色模式） | 取舍不同 | PRD 要求主题切换所以我做了；原项目没有这个需求，不算缺陷 |
| 设计 token 体系 | `tokens.css`：颜色 / 圆角 / 阴影十几个语义变量 | Tailwind v4 `@theme`：颜色 + 字体 + 四级圆角 + 四级阴影 + 缓动 + 6 组 keyframes + 自定义 utility | 原实现更优 | 我的 token 缺字号/间距/字体/动效层，组件一多就会各自硬编码 |
| 样式方案 | CSS Modules + 语义变量 | Tailwind v4（`@tailwindcss/vite`）+ `@theme` | 取舍不同 | Tailwind 迭代更快、一致性靠 token 兜；CSS Modules 零额外依赖、作用域天然隔离 |
| 无障碍与动效降级 | 无 | `:focus-visible` 统一焦点环 + `prefers-reduced-motion` 全局降级 | 漏项 | 骨架期定下来成本最低，后期补要改所有组件 |
| 通用 UI 组件 | 无，按钮样式写在页面级 CSS Module 里 | `components/ui/Button` + `buttonStyles`（variant/size/active/block 契约，Link 也能复用） | 漏项 | 第二个页面开始就会复制粘贴按钮样式 |
| 本地端口 / 代理目标 | `VITE_PROXY_TARGET` 可配，默认 8080；dev server 用默认 5173 | 硬编码：`host 127.0.0.1` + `port 7301` + `strictPort`，代理到 7302，与后端 `.env` 对齐 | 原实现更优 | 我的默认 8080 与真实后端 7302 不符，首次联调必踩；显式绑 127.0.0.1 还绕开了「Vite 只监听 ::1」的坑 |
| SSE 通道 | 只代理 `/api` | 额外代理 `/events`（后端 events router 故意挂在 `/api` 外） | 漏项 | M1 进度推送必踩，且 SSE 反代需要单独关缓冲 |
| 健康检查 | dev-only 面板（`isDev` + lazy，生产连 chunk 都不产出），按响应体 `error:` 前缀判定 | 前端完全不调 `/api/health`（后端有接口但无人用） | 我更优 | 联调期省事；代价是生产环境没有「后端不可达」提示（原实现同样没有） |
| 代码质量工具 | 只配了 `typecheck`（tsc -b） | oxlint + `lint` 脚本 + `.oxlintrc.json`（rules-of-hooks / only-export-components） | 漏项 | 骨架期接 lint 成本最低 |
| TS 严格度 | `strict: true` + `noUncheckedSideEffectImports` + `noFallthroughCasesInSwitch` | `tsconfig.app.json` 未开 `strict`（只有 noUnused* / erasableSyntaxOnly） | 我更优 | 原实现缺 strict，null / any 类问题只能靠人眼兜 |
| 目录分层 | `app/`（装配）+ `config/` + `lib/` + `routes/` + `dev/`，业务模块后续进 `features/` | 按技术类型平铺：`api/ components/ hooks/ lib/ layouts/ pages/ stores/` | 取舍不同 | 我按 bulletproof-react 走 feature 化；原实现平铺更简单，业务组件靠 `components/editor` 等子目录分 |

> - `原实现更优`：两边都做了，判断原实现更好
